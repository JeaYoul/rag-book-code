# 23장. 가장 소중한 것을 마지막에 — 사내 데이터

**이 폴더에는 실제 제품도 문서도 성분도 들어 있지 않다.** 구조와 원리만 있다.

23장에 이렇게 썼다. 책에 무엇을 쓰지 않을지 정하는 일과, 시스템이 무엇을 내보내지 않을지 정하는 일은 같은 일이다. 이 폴더는 그 두 번째 일을 코드로 옮긴 것이다.

## 파일

| 파일 | 역할 |
|---|---|
| `schema.sql` | 논문·제품·내부문서를 **같은 모양**으로 담되 **같은 자리에 담지 않는** 뼈대. 문서 등급과 등급별 뷰 |
| `patent_chunker.py` | 청구항은 자르지 않는다. `--compare` 로 자르면 무엇이 사라지는지 |
| `leak_check.py` | 내보내기 전에 한 번 더 본다. 등급에 따라 걸리는 것이 달라진다 |
| `search_internal.py` | 등급으로 걸러진 뷰만 읽는 검색. 제품 검색도 같은 함수 |
| `sample/patent_sample.txt` | 실제 특허의 모양을 흉내 낸 표본. 내용은 전부 지어낸 것 |

## 해보기 (데이터베이스 없이)

```bash
python patent_chunker.py sample/patent_sample.txt --max-chars 400 --compare
```

청구항 하나가 상한을 넘는데도 자르지 않는 것을 보여 준다. 그리고 `--compare` 는 문자 수로만 자르면 무엇이 사라지는지 보여 준다. 조각 2가 "투과도가"로 시작한다.

```bash
python leak_check.py --demo
python search_internal.py "층 구조로 안정성을 높이는 방법" --fake --level public
python search_internal.py "층 구조로 안정성을 높이는 방법" --fake --level restricted
python search_internal.py "질문" --fake --level confidential      # 만들지 않은 등급 — 거부한다
```

## 세 가지 설계 결정

**하나, 같은 모양으로 담되 같은 자리에 담지 않는다.**

논문 조각과 제품 조각과 내부문서 조각이 모두 "본체 표 + 조각 표 + 벡터" 모양이다. 그래야 16장에서 논문에 쓴 검색 코드를 그대로 쓸 수 있다. 그런데 스키마는 갈라 둔다. 검색 한 번이 실수로 두 종류를 긁어 오지 않게.

실제 시스템은 아직 한 자리에 있다. 그것이 3만 편을 아직 붓지 못한 이유 중 하나였다.

**둘, 문서에도 등급이 있다.**

사람만 등급을 나누면 안 된다. 한 덩어리로 보이는 자료 안에 이미 공개된 것과 공개되지 않은 것이 섞여 있다. 그래서 문서마다 등급을 붙이고, **기본값을 두지 않았다.**

```sql
sensitivity    internal.sensitivity NOT NULL,   -- 기본값 없음
classified_by  TEXT NOT NULL,                   -- 누가 붙였는가
```

기본값이 있으면 넣는 것을 잊었을 때 조용히 어느 등급으로 들어간다. 그리고 이 판단은 사람이 한다. 공개되었는지 아닌지를 기계가 판단하게 하지 않는다.

**셋, 애플리케이션은 표를 읽지 않고 뷰를 읽는다.**

```sql
CREATE VIEW internal.chunks_public     AS ... WHERE d.sensitivity = 'public';
CREATE VIEW internal.chunks_restricted AS ... WHERE d.sensitivity IN ('public','restricted');
```

`confidential` 을 포함하는 뷰는 만들지 않았다. 필요해지면 그때 만들고, 그때 한 번 더 생각한다. 그래서 검색은 등급 밖의 것을 **걸러 내는** 것이 아니라 **애초에 읽지 않는다.** 코드 한 곳에서 실수해도 나가지 않는다.

## 청구항을 자르지 않는 이유

15장에서 조각을 800자쯤으로 나누며 "문장 중간에서 자르지 말라"고 했다. 특허에서는 그 원칙이 더 강해진다.

청구항은 읽는 글이 아니라 **경계를 그리는 글**이다. 한 문장이 반 페이지가 되고, 낱말 하나가 권리 범위를 바꾼다. 반으로 자른 청구항은 뜻이 반이 되는 것이 아니라 **아예 다른 뜻**이 된다.

만들면서 알게 된 것이 하나 더 있다. **청구항은 대개 한 문장이다.** 그래서 15장의 문장 경계 규칙만으로는 애초에 자를 수 없다. 위험한 것은 문자 수만 세어 자르는 조각기다. `--compare` 가 그것을 보여 준다.

논문이라면 조각 하나가 부실해도 다른 조각이 메운다. 청구항은 메울 수 없다.

## 유출 검사기의 등급

같은 글이 어디로 나가는지에 따라 다르게 걸린다.

| 걸리는 것 | 사내 | 거래처 | 공개 |
|---|---|---|---|
| 자격 증명 | ● | ● | ● |
| 배합비 · 공정 조건 · 균주 번호 · 내부 문서번호 · 대외비 표시 | | ● | ● |
| 연락처 | | | ● |

자격 증명은 어느 등급에서도 걸린다. 사내 문서에도 있어서는 안 된다. 연락처는 공개용에서만 걸린다. 사내에서는 문제가 아니다.

**이 도구는 막지 않는다. 표시할 뿐이다.** 19장의 무인용 문단 가드와 같은 성격이다. 내보낼지 말지는 사람이 정한다.

## 정직하게

- **규칙은 자기 것으로 바꿔야 한다.** `leak_check.py` 의 `RULES` 는 본보기다. 실제 성분명·제품명·균주명은 이 책에 적지 않았고, 당신 회사의 것은 당신만 안다. 그 목록을 채우는 것이 이 파일을 쓰는 첫 일이다.
- `schema.sql` 의 칸 구성은 **실제 시스템의 것이 아니다.** 실제 칸 이름과 스키마는 이 책에 적지 않기로 했다. 여기 있는 것은 같은 방법을 자기 데이터에 쓰려는 사람을 위한 뼈대다.
- `sample/patent_sample.txt` 는 실제 특허의 **모양**만 흉내 낸 것이다. 내용은 전부 지어냈고, 어떤 실제 출원과도 관계가 없다.
- 이 저장소에서 자동 검증한 것: 특허 조각기(청구항 다섯 개가 상한과 무관하게 통째로, 잘린 청구항 0개, 문자 수로 자를 때의 손실), 유출 검사기(등급 셋 × 여섯 경우 행렬), 등급별 검색(공개·사내 뷰가 각각 무엇을 읽고 무엇을 읽지 않는가, 만들지 않은 등급 거부), 스키마 SQL의 구조와 괄호 균형.
- 실제 데이터베이스에 부어 보는 것은 **하지 않았다.** 이 폴더의 뜻이 그것이다. 붓기 전에 세워야 할 벽을 먼저 만드는 것.
