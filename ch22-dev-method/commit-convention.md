# 커밋 메시지 규칙

22장에서 실제로 쓴 규칙. 아홉 달 163커밋에 이렇게 적용되었다.

## 모양

```
<종류>: <무엇을 왜 바꿨는지 한 줄>

(필요하면) 왜 그렇게 했는지, 무엇을 시도했다 접었는지
```

## 종류

| 접두어 | 뜻 | 실제 건수 |
|---|---|---|
| `feat:` | 새 기능 | 52 |
| `fix:` | 고침 | 40 |
| `refactor:` | 동작은 같고 구조만 정리 | 10 |
| `docs:` | 문서 | 4 |
| `ops:` | 운영·배포·설정 | 2 |
| `chore:` | 잡일 | 2 |
| `security:` | 보안 | 1 |
| `revert:` | 되돌림 | 1 |
| `restore:` | 되살림 | 1 |

## 한 줄에 무엇을 적는가

**무엇을 고쳤는가가 아니라 왜 고쳤는가.** 파일 이름과 함수 이름은 diff 를 보면 안다.
반년 뒤에 남는 것은 이 한 줄뿐이다.

좋은 예 (실제 커밋에서):

```
fix: 리랭커 청크 단위 채점 및 메모리 절감 (MAX_DOCS/CHUNK_SIZE)
fix: 리랭커 HTTP 타임아웃 config 편입 (10s→30s, 60건 요청 실측 13~16s)
```

두 번째 것을 보라. **실측값이 들어 있다.** 왜 30초인지가 메시지에 남았다.
20장에서 그 장애를 되짚을 때, 시스템 로그는 이미 지워져 있었고 이 한 줄이 남아 있었다.

나쁜 예:

```
fix: 버그 수정
update
수정
```

## 얼마나 자주 커밋하는가

되돌아갈 지점이 필요한 만큼. 규칙은 하나다.
**AI 에게 큰 변경을 시키기 전에 커밋한다.** 그러면 망쳐도 되돌릴 수 있고,
되돌릴 수 있으면 마음껏 시킬 수 있다.

## AI 와 함께 쓴 커밋

도구가 만들어 준 변경을 커밋할 때는 그것을 표시해 두는 편이 낫다.
누가 썼는지가 아니라, **나중에 그 부분을 볼 때 참고가 되기 때문**이다.

```
Co-Authored-By: <도구 이름> <noreply@example.com>
```

## 되돌리기

```bash
git log --oneline -20                 # 어디로 돌아갈지 고른다
git revert <커밋>                      # 그 변경만 취소하는 새 커밋 (역사를 남긴다)
git checkout -- <파일>                 # 아직 커밋하지 않은 변경을 버린다
```

`revert` 를 쓰면 되돌린 기록도 역사에 남는다. 그것이 `reset` 보다 나은 이유다.
무엇을 시도했다 접었는지가 남는다.
